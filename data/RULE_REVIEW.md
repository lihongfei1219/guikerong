# 产品库与规则维护

`product_rules.json` 是初始规则草稿，按平台产品 ID 保存。它引用本地 CSV，未验证平台当前状态，也不代表银行授信审批。

- 36 条 CSV 记录按产品 ID 合并为 35 个产品。科技转化贷两条记录仅详情 URL 的页码不同；创新积分贷的两个不同银行产品分别保留。
- 科企订单贷的申请条件在“与借款人建”处截断，导入时标记 `UNAVAILABLE`。补齐完整源数据后仍须重新复核规则。
- 八个产品已经拆成可解释的条件树：科企贷、智企贷、农银广西创新积分贷、招商科创贷、出口闪贷、跨境直贷通、工行科创 e 贷、浙商专精特新贷。其他产品完整保留申请条件及适用客户原文，使用 `manual` 条件。所有原子条件均由模型结合全部企业原文判断，银行认定等不能代替核验的事项仍返回待核验。
- 所有真实产品初始均为 `DRAFT` / `SNAPSHOT`。模型结论可诊断，但正式推荐须经过服务层发布状态检查。

## 来源与版本

`source_rows` 是 CSV 逻辑记录号，表头计为第 1 条；带引号的多行单元格仍算一条记录。`raw_fields` 保留原始列；重复记录的原文及 URL 放在 `_source_records_json`。

`source_record_sha256` 绑定产品所有原始字段，只忽略首尾空白及详情 URL 的分页参数。任意源内容变化都会撤销旧规则的复核状态，退回完整原文的待核验规则。目录版本同时包含 CSV 原始文件和规则 JSON 的完整 SHA-256，便于复现每次匹配。

## 复核和激活流程

1. 核对产品来源、完整申请条件、适用客户、主体、时间、单位、AND/OR、豁免和有效期；发现截断或相同 ID 内容冲突时先修复源数据。
2. 编辑该产品的规则树，保留逐项 `source_field` / `source_quote`；未定义口径、未接通证据或银行独立审批条款继续使用 `manual`，不得删除它们来取得通过。
3. 比较全部源内容，使用 `app.catalog.source_record_hash(raw_fields)` 取得当前内容哈希；更新 `source_record_sha256`，递增 `rule_version`，执行相关测试和业务复核。
4. 由实际业务复核人填写 `rule_review` 对象的 `reviewer`、`reviewed_at`、`evidence_reference`，将 `rule_status` 改为 `REVIEWED`。这些记录只是项目规则复核记录，不能被描述为银行审批结果。
5. 通过真实产品来源确认产品仍可申请，填写同样结构的 `availability_verification`，将 `availability_status` 改为 `ACTIVE`；产品失效后改为 `UNAVAILABLE` 并填写 `unavailable_reason`。本地元数据不能代替实时银行核验；应按运营周期重新核验可用性。

导入器检查来源哈希、引文和发布记录是否存在，不验证外部证明真实性，也不会自动审核规则。修改 JSON 文件后需重新加载服务产品库。企业固定模板解析器已经删除，每个产品以独立协程将全部企业原文与该产品资料交给模型；`field_id`、运算符和阈值等仍作为产品规则说明，不要求企业提供同名字段。模型需核对主体、时期、单位和原文证据，不能混用关联企业资料。产品条件树、原文覆盖及审核门槛继续保留。

`build_initial_rules.py` 仅用于从仓库初始 CSV 生成第一版草稿，已有规则文件时拒绝覆盖。日常维护应直接复核版本化 JSON，避免重新生成抹掉人工审核工作。
